▶ Kickoff prompt — Auto Concierge MVP 
Gradimo MVP web aplikacije "Auto Concierge" — concierge servis za vozila u Novom Sadu (preuzimanje vozila sa adrese → odvoz na servis/tehnički/gume/pranje → vraćanje). Puna specifikacija je u priloženom HTML dokumentu (auto-concierge-spec.html) i landing stranici (index.html). Pročitaj oba pre nego što počneš.

TEHNOLOGIJA
- Next.js 14+ (App Router, TypeScript), Tailwind CSS
- Firebase: Auth (email+lozinka + Google/Apple), Firestore, Cloud Functions, Cloud Messaging (web push), Storage
- Jedna web aplikacija, responsive/PWA, role-based UI

TRI ULOGE (razdvojene kroz UI, ne tri aplikacije)
- client  — registruje se sam; mobile-first
- dispatcher — interni nalog; desktop
- driver  — interni nalog; mobile-first
Uloga se čita iz polja `role` na korisniku (custom claim + users dokument), pa root layout svake role-grupe postavlja data-role i odgovarajući akcent.

DIZAJN (kritično: app mora da izgleda kao landing)
- Izvuci tokene iz index.html: tamna zeleno-ugljena podloga (#0d1410), brass akcenat, fontovi Sora/Inter/JetBrains Mono, radijusi i senke. Primeni ih kao globalne tokene.
- Razlika po ulozi je SAMO akcentna boja (sve ostalo identično):
    client → #c9a86a (zlatna)
    dispatcher → #6fd3a3 (mint)
    driver → #e0954a (amber)
- Komponente koriste var(--role-accent), ne fiksne boje.

SUŠTINA TOKA
Klijent kreira zahtev (vozilo + jedna ili više usluga, svaka usluga ima svoju destinaciju i izbor "vaš predlog" ili "moj serviser"; adresa preuzimanja + adresa vraćanja + vremenski okvir). Dispečer sastavlja ponudu (tačan termin, cena prevoza, bira partnere za "vaš predlog" stavke, može menjati stavke) → klijent potvrđuje/odbija → dispečer ručno dodeljuje vozača → vozač vodi statuse i pravi foto PRE (preuzimanje) i POSLE (vraćanje) → dispečer zatvara posao. Statusi: CREATED → OFFER_SENT → CONFIRMED → DRIVER_ASSIGNED → PICKED_UP → AT_SERVICE → SERVICE_DONE → RETURNING → DELIVERED → CLOSED (+ REJECTED/CANCELLED).

VAN OBIMA MVP-a: pretplata, in-app plaćanje, live GPS, B2B flote, auto-dodela vozača, partner interfejs, chat. (Naplata prevoza je van app; uslugu klijent plaća direktno serviseru.)

KAKO DA RADIMO
Idemo fazno (F1→F6 iz specifikacije). PRVO u F1 reši auth bootstrap (seed admina/dispečera, custom claims, createDriver Cloud Function) — bez toga niko ne može da uđe kao dispečer. Validaciju prelaza statusa radi i u Cloud Functions, ne samo u sigurnosnim pravilima. Ispoštuj sekcije o validaciji formi (11A), greškama i edge slučajevima (11B), notifikacijama sa in-app fallback-om (9A) i otpornom upload-u na terenu (10). Ne uvodi funkcije van obima MVP-a bez pitanja. Pre koda u F1, predloži strukturu foldera, package.json i Firestore inicijalizaciju, pa sačekaj moju potvrdu.

Počni tako što ćeš pročitati specifikaciju i landing, ukratko mi potvrditi razumevanje obima, pa predložiti F1 strukturu.

1Pregled i obim

Auto Concierge je premium usluga upravljanja vozilom: korisnik zakazuje preuzimanje svog vozila sa zadate adrese, mi ga odvozimo na željenu uslugu (servis, tehnički pregled, registracija, zamena guma, pranje/detailing) i vraćamo na izabranu adresu. Poslovni model je asset-light — koristimo partnersku mrežu servisera i sopstvene/angažovane vozače.

Šta MVP radi

  • Klijent kreira zahtev sa jednim vozilom i jednom ili više usluga, gde svaka usluga ima svoju destinaciju (serviser).
  • Za svaku uslugu klijent bira: „vaš predlog" (partnera bira dispečer) ili „moj serviser" (klijent upisuje/bira sačuvanog).
  • Dispečer pregleda zahtev, sastavlja ponudu (tačan termin, cena prevoza, eventualne izmene stavki, konkretni partneri za „vaš predlog").
  • Klijent potvrđuje ili odbija ponudu. Po potvrdi posao postaje aktivan.
  • Dispečer ručno dodeljuje vozača. Vozač vodi posao kroz statuse i pravi foto-dokumentaciju pre i posle.
  • Klijent prati status u realnom vremenu i dobija notifikacije. Po završetku vidi posao u istoriji.

Ključne granice obima

  • Bez pretplate u MVP-u — sve se vodi po zahtevu.
  • Naplata prevoza je van aplikacije (keš/transfer). Mi naplaćujemo samo prevoz; uslugu klijent plaća direktno serviseru.
  • Bez live GPS-a — status zamenjuje praćenje na mapi.
  • Partner nema interfejs — vozač/dispečer vode njegov status.
  • Bez in-app chata — komunikacija preko statusa, notifikacija i telefona.

Implementacija (predlog)

Akcent se postavlja jednom, na nivou role-layout-a, kao CSS varijabla. Komponente koriste var(--role-accent) umesto fiksne boje, pa se isti dugmići/badge-evi automatski prebojavaju po ulozi.

/* globalni tokeni — isti svuda */
:root {
  --bg: #0d1410; --bg-2: #111b15; --surface: #15211a;
  --border: #243a2d; --text: #eef2ed; --text-dim: #9db0a3;
}
/* akcent se vezuje za ulogu na wrapper elementu */
[data-role="client"]     { --role-accent: #c9a86a; }
[data-role="dispatcher"] { --role-accent: #6fd3a3; }
[data-role="driver"]     { --role-accent: #e0954a; }

/* komponente koriste promenljivu, ne fiksnu boju */
.btn-primary { background: var(--role-accent); color: #11150f; }
.status-step.active .node { background: var(--role-accent); }
.role-badge { color: var(--role-accent); border-color: var(--role-accent); }

U Next.js-u: data-role se postavlja na root layout svake role-grupe ((client), (dispatcher), (driver)) na osnovu role iz korisničkog profila. Tailwind varijanta: definiši roleAccent kao CSS var i mapiraj je u tailwind.config kao boju accent.

Pravila doslednosti

  • Podloga, tipografija, radijusi, senke i raspored — identični za sve tri uloge i za sajt.
  • Menja se samo akcent. Nikad ne uvoditi drugu pozadinsku boju ili font po ulozi.
  • Badge uloge stoji u zaglavlju app-a (gore), da korisnik uvek zna „gde je“ — naročito bitno za naloge koji bi mogli da imaju više uloga u budućnosti.
  • Mint (dispečer) se na sajtu već koristi za „UŽIVO“ indikator — u app-u zadržava isto značenje (živo/aktivno), pa nema konflikta.
  • Kontrast: sva tri akcenta su testirana na tamnoj podlozi; tekst na dugmadima je tamni (#11150f) radi čitljivosti.

Autentifikacija

  • Klijent: Email + lozinka kao primarni metod, plus Google i Apple sign-in. Broj telefona se obavezno čuva u profilu (dispečeru treba za poziv), ali nije metod prijave.
  • Dispečer i vozač: naloge kreira administrator (interno). U MVP-u dovoljno je ručno kreiranje preko Firebase konzole ili jednostavnog admin skripta.
  • Uloge preko custom claims: role se postavlja kao Firebase Auth custom claim (preko Cloud Function), a duplira se i u users dokumentu radi lakšeg čitanja na klijentu i u sigurnosnim pravilima.

3A · Onboarding naloga i bootstrap administratora

Kritično za prvi start. Bez ovoga niko ne može da se uloguje kao dispečer i aplikacija je prazna ljuska. Ovo je prva stvar koju treba rešiti u F1.

Kako se postavlja uloga

  • role se čuva na dva mesta: kao Firebase Auth custom claim (za sigurnosna pravila i guard-ove) i u users/{uid} dokumentu (za čitanje na klijentu).
  • Custom claim može da postavi samo Cloud Function sa admin privilegijama — klijent nikad ne sme sam sebi da dodeli ulogu.
  • Novi korisnik koji se sam registruje automatski dobija role: 'client' (podrazumevano, postavlja ga Auth onCreate Cloud Function).

Bootstrap prvog administratora/dispečera

Pošto dispečera ne može da kreira drugi dispečer ako nijedan ne postoji, treba seed procedura:

// scripts/seed-admin.ts — pokreće se lokalno jednom, sa Firebase Admin SDK
// (servisni ključ NIJE u repo-u; čita se iz env varijable ili lokalnog fajla van git-a)
import admin from 'firebase-admin';
admin.initializeApp({ credential: admin.credential.cert(/* iz env */) });

const uid = process.argv[2];           // uid postojećeg naloga
const role = process.argv[3] || 'dispatcher';
await admin.auth().setCustomUserClaims(uid, { role });
await admin.firestore().doc(`users/${uid}`).set({ role }, { merge: true });
console.log(`Postavljena uloga ${role} za ${uid}`);

Postupak: 1) napravi nalog kroz registraciju, 2) iskopiraj njegov uid iz Firebase konzole, 3) pokreni npx tsx scripts/seed-admin.ts <uid> dispatcher. Korisnik se mora odjaviti i ponovo prijaviti da bi novi claim ušao u token.

Kreiranje vozača i ostalih dispečera (u aplikaciji)

  • Kad dispečer postoji, on iz panela (/drivers) kreira vozače. To poziva Cloud Function createDriver (callable, dozvoljena samo za role==='dispatcher') koja: pravi Auth nalog, postavlja role:'driver' claim, kreira users dokument, i šalje vozaču privremenu lozinku (ili link za postavljanje lozinke).
  • Isti obrazac za kreiranje dodatnih dispečera (callable createDispatcher).
  • Promena tokena: nakon što Function postavi claim, klijent mora da pozove getIdToken(true) da osveži token pre nego što guard prepozna ulogu.

4Model podataka (Firestore)

Glavni princip: zahtev se sastoji od stavki (services), gde svaka stavka ima svoju uslugu i destinaciju. Jedan zahtev može voditi vozilo na više lokacija.

Kolekcija users

users/{uid} {
  role: 'client' | 'dispatcher' | 'driver'
  fullName: string
  email: string
  phone: string
  createdAt: timestamp
  fcmTokens: string[]          // za web push
  // samo za driver:
  isActive?: boolean           // da li je trenutno raspoloživ
}

Podkolekcija users/{uid}/vehicles (samo klijent)

vehicles/{vehicleId} {
  make: string                 // marka (npr. Volkswagen)
  model: string                // model (npr. Golf 7)
  year: number                 // godište
  plate?: string               // registracija (opciono)
  note?: string                // npr. boja, posebne napomene
  createdAt: timestamp
}

Podkolekcija users/{uid}/servicers (sačuvani serviseri klijenta)

servicers/{servicerId} {
  name: string                 // npr. "Auto-servis Pera"
  address: string
  phone?: string
  serviceTypes?: string[]      // npr. ['tire','technical'] — opciono
  createdAt: timestamp
}

Kolekcija partners (naša partnerska mreža — vodi dispečer)

partners/{partnerId} {
  name: string
  address: string
  phone: string
  serviceTypes: string[]       // koje usluge pokriva
  note?: string
  isActive: boolean
  createdAt: timestamp
}

Kolekcija requests (srce sistema)

requests/{requestId} {
  clientId: string             // uid klijenta
  status: RequestStatus        // vidi tok ispod
  createdAt: timestamp
  updatedAt: timestamp

  // vozilo (snapshot u trenutku kreiranja — ne referenca,
  // da istorija ostane tačna i ako klijent obriše vozilo)
  vehicle: {
    vehicleId?: string         // ref na sačuvano (ako postoji)
    make: string
    model: string
    year: number
    plate?: string
  }

  // logistika
  pickup: {
    address: string
    lat?: number
    lng?: number
    timeWindow: {              // vremenski okvir, ne tačan sat
      date: string             // 'YYYY-MM-DD'
      from: string             // 'HH:mm'
      to: string               // 'HH:mm'
    }
  }
  dropoff: {                   // mesto vraćanja — klijent bira
    address: string
    lat?: number
    lng?: number
    sameAsPickup: boolean
  }

  // STAVKE — svaka usluga svoja destinacija
  services: ServiceItem[]

  // ponuda (popunjava dispečer)
  offer?: {
    proposedTime: string       // tačan predloženi termin
    transportPrice: number     // cena prevoza (RSD) — naš prihod
    note?: string
    createdAt: timestamp
    createdBy: string          // uid dispečera
  }
  offerRespondedAt?: timestamp // kad je klijent odgovorio
  rejectionReason?: string

  // izvršenje
  assignedDriverId?: string
  assignedAt?: timestamp

  // foto-dokumentacija (URL-ovi iz Storage)
  photosBefore?: string[]
  photosAfter?: string[]

  cancelledBy?: 'client' | 'dispatcher'
  cancelReason?: string
}

Tip ServiceItem

ServiceItem {
  id: string                   // lokalni id stavke
  type: 'service' | 'technical' | 'registration' | 'tires' | 'wash' | 'other'
  label?: string               // za 'other' ili dodatni opis

  // izbor servisera za OVU stavku:
  servicerChoice: 'suggest' | 'own'
  //  'suggest' → dispečer bira partnera (popunjava partnerRef u ponudi)
  //  'own'     → klijent je zadao servisera

  // ako 'own':
  ownServicer?: {
    servicerId?: string        // ref na sačuvanog servicera
    name: string
    address: string
    phone?: string
  }

  // ako 'suggest' — dispečer popunjava u ponudi:
  partnerRef?: {
    partnerId: string
    name: string
    address: string
    phone: string
  }

  // status po stavki (vodi vozač/dispečer):
  itemStatus?: 'pending' | 'at_servicer' | 'done'
}
Napomena o snapshotima. Vozilo i serviser se u request upisuju kao snapshot (kopija vrednosti), ne samo kao referenca. Razlog: ako klijent kasnije izmeni ili obriše vozilo/servisera, istorijski zahtev mora ostati tačan. Referenca (vehicleId, servicerId) se čuva dodatno, ali prikaz se oslanja na snapshot.

Pravila prelaza (validacija u Cloud Function)

  • Prelaz iz OFFER_SENT nazad u CREATED dozvoljen ako klijent traži izmenu (umesto čistog odbijanja).
  • PICKED_UP ne može bez bar jedne fotografije u photosBefore.
  • DELIVERED ne može bez bar jedne fotografije u photosAfter.
  • Otkazivanje (CANCELLED) dozvoljeno klijentu samo do DRIVER_ASSIGNED; posle toga otkazuje dispečer.
  • Svaki prelaz upisuje updatedAt i (opciono) zapis u requests/{id}/history podkolekciju radi audit traga.

6Ekrani — Klijent MVP

6.1 Početna (/home)

  • Lista zahteva podeljena na Aktivni i Istorija.
  • Svaka kartica: vozilo, usluge (čip po stavci), status badge, datum.
  • Aktivni zahtevi se ažuriraju u realnom vremenu (Firestore listener).
  • Veliko dugme „Novi zahtev".

6.2 Kreiranje zahteva (/new) — višekorakni tok

  1. Vozilo: bira sačuvano iz liste ili unosi novo (marka, model, godište, opciono registracija). Novo se može sačuvati u profil.
  2. Usluge (stavke): dodaje jednu ili više usluga. Za svaku:
    • tip usluge (servis, tehnički, registracija, gume, pranje, ostalo)
    • izbor servisera: „Predložite vi" ili „Moj serviser"
    • ako „moj serviser": bira iz sačuvanih ili unosi novog (naziv, adresa, telefon) — može sačuvati za ubuduće
  3. Preuzimanje: adresa + vremenski okvir (datum, od–do).
  4. Vraćanje: checkbox „isto kao preuzimanje" ili unos druge adrese.
  5. Pregled i slanje: rezime celog zahteva, dugme „Pošalji zahtev" → status CREATED.

6.3 Detalj zahteva (/request/[id])

  • Traka statusa (stepper) sa trenutnom fazom.
  • Kad stigne ponuda (OFFER_SENT): prikaz predloženog termina, cene prevoza, konkretnih partnera za „predložite vi" stavke, pa dugmad Prihvati / Odbij / Traži izmenu.
  • Kad je posao aktivan: prikaz dodeljenog vozača (ime, telefon za poziv), stavke sa destinacijama.
  • Po završetku: galerija foto pre/posle.
  • Dugme „Otkaži" (vidljivo samo do faze DRIVER_ASSIGNED).

6.4 Moja vozila (/vehicles) i Moji serviseri (/servicers)

  • CRUD nad sačuvanim vozilima i serviserima — da se ubrzava buduće kreiranje zahteva.

7Ekrani — Dispečer MVP

7.1 Tabla (/board) — desktop kanban

  • Kolone po statusu: Novi (CREATED) · Ponuda poslata · Potvrđeni · U toku · Završeni.
  • Kartica zahteva: klijent, vozilo, broj stavki, vremenski okvir, badge ako neka stavka traži „predložite vi" (zahteva akciju).
  • Realtime ažuriranje. Klik otvara detalj.
  • Filteri: po statusu, po datumu, „samo oni koji čekaju ponudu".

7.2 Detalj + sastavljanje ponude (/request/[id])

  • Pun pregled zahteva: vozilo, sve stavke sa destinacijama, preuzimanje/vraćanje, klijent (sa telefonom).
  • Sastavljanje ponude:
    • za svaku „predložite vi" stavku — bira partnera iz mreže (partners), filtrirano po tipu usluge
    • može dodati / izmeniti / ukloniti stavke (npr. doda overu uz tehnički)
    • unosi tačan predloženi termin i cenu prevoza
    • opciona napomena
    • dugme „Pošalji ponudu" → OFFER_SENT
  • Po potvrdi klijenta: dodela vozača — padajuća lista aktivnih vozača → DRIVER_ASSIGNED.
  • Praćenje izvršenja i ručno vođenje partnerovog statusa po stavci (itemStatus).
  • Dugme „Zatvori posao" (CLOSED) nakon DELIVERED.

7.3 Vozači (/drivers) i Partneri (/partners)

  • Upravljanje vozačima (status aktivan/neaktivan) i partnerskom mrežom (CRUD: naziv, adresa, telefon, tipovi usluga).

8Ekrani — Vozač MVP

8.1 Moji poslovi (/jobs) — mobile-first

  • Lista dodeljenih poslova sortirana po vremenskom okviru preuzimanja.
  • Kartica: vozilo, adresa preuzimanja, vreme, trenutni status, broj destinacija.

8.2 Detalj posla (/job/[id])

  • Sve informacije za teren: vozilo, klijent (telefon), adresa preuzimanja, destinacije po stavkama (sa telefonima servisera/partnera), adresa vraćanja.
  • Akciona dugmad po fazi (veliki touch targets):
    • „Preuzeo sam vozilo" → traži upload foto PRE → PICKED_UP
    • „Predao serviseru" → AT_SERVICE
    • „Usluga gotova" → SERVICE_DONE
    • „Vozim nazad" → RETURNING
    • „Predao klijentu" → traži upload foto POSLE → DELIVERED
  • Foto-upload: direktno sa telefonske kamere, više slika, kompresija pre slanja.

9A · Dozvole, fallback i pouzdanost

Web push nije garantovan. Korisnik može odbiti dozvolu, a na iOS-u push radi samo ako je PWA dodata na home screen. Zato push nikad nije jedini kanal — uvek postoji in-app fallback.

In-app notifikacije kao osnova (uvek rade)

  • Kolekcija users/{uid}/notifications — svaki događaj se upisuje ovde, bez obzira na push.
  • Aplikacija sluša ovu kolekciju realtime i prikazuje badge sa brojačem (zvonce u zaglavlju) + listu obaveštenja.
  • Pošto i klijent i vozač ionako gledaju svoj ekran sa realtime statusom, ovo pokriva slučaj kad push ne stigne.
users/{uid}/notifications/{notifId} {
  type: 'offer_sent' | 'driver_assigned' | 'status_changed' | ...
  requestId: string
  title: string
  body: string
  read: boolean
  createdAt: timestamp
}

Web push (nadogradnja, ne osnova)

  • Traži: service worker (firebase-messaging-sw.js), VAPID ključ, i eksplicitno traženje dozvole.
  • Kada tražiti dozvolu: ne odmah na učitavanju — nego posle prve smislene akcije (klijent posle prvog zahteva, vozač pri prvom loginu), uz kratko objašnjenje zašto.
  • FCM token se čuva u users/{uid}.fcmTokens[]. Token se može promeniti/isteći — osvežavati ga pri svakom loginu i čistiti nevažeće kad slanje vrati grešku.
  • Ako korisnik odbije dozvolu — nema ponavljanog pitanja; oslanjamo se na in-app badge.

Posebno za vozača

Dodela posla je vremenski osetljiva. Pored push + in-app badge, na /jobs ekranu novi dodeljen posao je vizuelno istaknut (amber traka „Novi posao"), pa vozač ne propušta posao ni ako je push promašio.

10Fotografije i Storage

  • Putanja: requests/{requestId}/before/{timestamp}.jpg i .../after/{timestamp}.jpg.
  • Klijentska kompresija pre upload-a (npr. browser-image-compression) — cilj ~1–1.5 MB po slici.
  • URL-ovi se upisuju u photosBefore[] / photosAfter[] na zahtevu.
  • Pristup čitanju: klijent (vlasnik), dodeljeni vozač, svi dispečeri.

Upload na terenu (slab signal)

Vozač često slika u garaži/podzemnom parkingu bez signala. Upload mora da bude otporan na to.
  • Optimistično ponašanje: slika se odmah prikaže lokalno (preview iz blob-a), status se ne menja dok upload ne uspe.
  • Retry red: ako upload padne, slika ostaje u redu i pokušava ponovo kad se mreža vrati (Firebase SDK ima ugrađeni resumable upload; dodatno čuvati u memoriji/IndexedDB dok ne prođe).
  • Blokada prelaza statusa: PICKED_UP / DELIVERED se ne potvrđuju dok bar jedna slika nije stvarno otpremljena (URL upisan) — sprečava „izgubljene" foto-dokaze.
  • Jasan indikator vozaču: „Otpremanje… / Otpremljeno ✓ / Greška, pokušaj ponovo".

11Sigurnosna pravila (smernice)

// Firestore (pseudo-pravila)
match /users/{uid} {
  allow read, write: if request.auth.uid == uid
                     || hasRole('dispatcher');
}
match /requests/{id} {
  allow create: if hasRole('client') && request.resource.data.clientId == request.auth.uid;
  allow read:   if resource.data.clientId == request.auth.uid
                || hasRole('dispatcher')
                || resource.data.assignedDriverId == request.auth.uid;
  allow update: if hasRole('dispatcher')
                || (isOwnerClient() && allowedClientTransition())
                || (isAssignedDriver() && allowedDriverTransition());
}
match /partners/{id} {
  allow read:  if isSignedIn();
  allow write: if hasRole('dispatcher');
}
// hasRole čita custom claim postavljen Cloud Function-om

Sve kritične validacije prelaza statusa rade se i u Cloud Function-u, ne samo u pravilima — pravila sprečavaju neovlašćen pristup, Function osigurava ispravan tok.

11B · Stanja grešaka i edge slučajevi

Prazna stanja (empty states)

  • Klijent bez zahteva: poruka + dugme „Napravi prvi zahtev".
  • Dispečerska tabla bez zahteva: prazne kolone sa diskretnom porukom.
  • Vozač bez poslova: „Trenutno nemaš dodeljenih poslova".

Konkurentnost i konflikti

  • Dvostruka dodela vozača: dodela ide kroz Cloud Function/transakciju koja proverava da posao još nije dodeljen — drugi dispečer dobija poruku „posao je već dodeljen".
  • Zastareli status: ako klijent gleda ponudu koju je dispečer u međuvremenu povukao/izmenio, akcija „Prihvati" proverava aktuelni status pre izvršenja.
  • Otkazivanje u letu: ako klijent otkaže baš dok dispečer dodeljuje vozača — Function odbija nevalidan prelaz, UI osvežava stvarno stanje.

Greške mreže i operacija

  • Svaka akcija (slanje zahteva, ponude, promena statusa) ima tri stanja: u toku (spinner, dugme zaključano), uspeh, greška (poruka + „Pokušaj ponovo").
  • Nikad „tiha" greška — ako nešto padne, korisnik vidi jasnu poruku, ne prazno.
  • Idempotentnost: dupli klik na „Pošalji" ne sme da napravi dva zahteva (zaključati dugme dok traje operacija).

Auth edge slučajevi

  • Token bez uloge još učitan (tek registrovan): prikazati učitavanje dok claim ne stigne, ne praznu stranicu.
  • Korisnik pristupa ruti van svoje uloge: redirect na svoj home, ne greška.
  • Istekla sesija: redirect na login sa porukom.
